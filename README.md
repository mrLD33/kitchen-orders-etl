# kitchen-orders-etl

Небольшой ETL-инструмент для производителя кухонь на заказ. Консолидирует CRM и
три Excel-таблицы, выявляет расхождения, просрочки и неполные данные, показывает
предварительную маржинальность по прямым затратам. Предназначен для демонстрации
автоматизации бизнес-процессов и работы аналитика с качеством данных.

Компания получает единый реестр вместо ручной сверки четырёх источников.
Ошибки не скрываются: их можно отфильтровать и передать ответственному сотруднику.
Приложение не исправляет источники и не выполняет синхронизацию с внешней CRM.
Платные сервисы, внешние API и учётные данные не нужны.

## Быстрый запуск

Требуется Python **3.12**. Выполняйте команды из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

Windows PowerShell: `py -3.12 -m venv .venv`, затем
`.venv\Scripts\Activate.ps1`, остальные команды аналогичны.

В браузере откройте локальный адрес, который выводит Streamlit.
Нажмите **«Загрузить демонстрационные данные»**. Далее откройте аналитику,
реестр, контроль качества и отчёты. Дату оценки сроков можно изменить в боковой
панели. Встроенный ZIP можно скачать и повторно загрузить через режим ZIP.

Режимы загрузки:

1. Один ZIP с четырьмя файлами; допускается общая вложенная директория.
2. Четыре файла, каждый в предназначенное для него поле загрузки.
3. Встроенные демонстрационные данные без пользовательских файлов.

При ошибке формата весь новый набор отклоняется, предыдущий отчёт остаётся.
Ошибки содержимого (даты, суммы, статусы и т. п.) не препятствуют сохранению
исходных строк: некорректные ячейки нормализуются в NULL и попадают в реестр проблем.
Счётчики загруженных строк включают дубли и записи без соответствия в CRM.

## Архитектура и технологии

Python 3.12, Streamlit, Pandas, SQLite из стандартной библиотеки, OpenPyXL,
Plotly и Pytest. Версии прямых зависимостей закреплены в `requirements.txt`.

```text
kitchen-orders-etl/
├── app.py                     # интерфейс на русском, состояние сессии
├── requirements.txt
├── pytest.ini
├── README.md
├── .gitignore
├── .streamlit/config.toml     # лимит загрузки, отключение телеметрии
├── src/
│   ├── __init__.py
│   ├── loader.py              # CSV, Excel, безопасный ZIP
│   ├── validator.py           # нормализация и правила качества
│   ├── database.py            # таблицы, SQL VIEW с LEFT JOIN
│   └── analytics.py           # сроки, финансовая надёжность, KPI, CSV
├── demo_data/
│   ├── crm_orders.csv
│   ├── measurements.xlsx
│   ├── production.xlsx
│   └── installation.xlsx
├── scripts/
│   ├── generate_demo.py       # генератор; не перезаписывает готовые файлы
│   └── setup_environment.sh   # повторная настройка /workspace в Codex
└── tests/
    ├── conftest.py
    ├── test_loader.py
    ├── test_validator.py
    ├── test_database.py
    ├── test_analytics.py
    └── test_app.py             # функциональный сценарий Streamlit AppTest
```

Поток обработки: файлы → исходные DataFrame → проверка и нормализация →
SQLite → SQL-представление → финансовые и временные показатели → интерфейс/CSV.

Четыре исходные таблицы `crm_orders`, `measurements`, `production`,
`installation` сохраняют все загруженные записи и ненормализованные значения
как текст (пустые ячейки — SQL NULL). Соответствующие четыре таблицы
`normalized_*` содержат приведённые значения и номер записи с учётом заголовка.
Суммы в них имеют тип REAL, даты — ISO TEXT, логические значения — INTEGER.
Исходные файлы при этом не изменяются.

SQL `orders_view` определён в `src/database.py`. В каждом источнике
`ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY row_number)` выбирает
**первую строку файла**, затем выполняются три LEFT JOIN относительно CRM.
Дубли не суммируются, не заменяются автоматически «лучшей» записью и не удаляются
из исходных таблиц. Это сохраняет одну строку на уникальный непустой номер CRM.
Пользователь видит предупреждение об этой политике и может сверить оригиналы.
Номер заказа без CRM и пустой номер Excel показываются отдельно; эти записи не
включаются в стоимость и количество заказов CRM. Пустой номер CRM — ошибка,
такой заказ невозможно включить в объединение.

Каждая загрузка создаёт новую базу SQLite `:memory:` в `st.session_state`.
Нет общей базы на диске, глобальных подключений или кеша пользовательских данных.
Повторная загрузка закрывает предыдущую базу после успешного построения нового
отчёта. Кнопка очистки удаляет набор текущей сессии. Перезапуск сервера или потеря
сессии удаляют данные; CSV следует скачать до завершения работы.

## Форматы входных данных

Имена столбцов регистрозависимы, внешние пробелы заголовков удаляются.
Все перечисленные столбцы обязательны; дополнительные игнорируются.
В отдельных полях загрузки имя файла может отличаться, в ZIP нужны точные имена.
ZIP проверяется без извлечения на диск. Неизвестные файлы не загружаются.

| Файл | Столбцы |
| --- | --- |
| `crm_orders.csv` | order_id, client_name, dealer, manager, order_date, planned_delivery, sale_amount, crm_status |
| `measurements.xlsx` | order_id, measurer, planned_date, actual_date, measurement_status, design_approved, specification_ready |
| `production.xlsx` | order_id, production_stage, production_start, planned_finish, actual_finish, materials_cost, labor_cost, other_cost |
| `installation.xlsx` | order_id, installer, planned_date, actual_date, installation_status, installation_cost, delivery_cost, complaint |

Правила значений:

- CSV: UTF-8/UTF-8 с BOM; запятая или точка с запятой; стандартное экранирование
  кавычками. Строка с числом полей, отличным от заголовка, отклоняет файл.
- Excel: `.xlsx`, первый лист, первая строка — заголовки. Формулы не вычисляются:
  вместо формул в датах/суммах нужны значения. Остальные листы не импортируются.
- `order_id` приводится к строке с обрезкой внешних пробелов; ведущие нули CSV
  и текстовых ячеек Excel сохраняются. Храните номер как текст во всех источниках:
  формат отображения Excel `000` не восстанавливает нули числовой ячейки.
- Даты: `YYYY-MM-DD`, `ДД.ММ.ГГГГ` или настоящая дата Excel. Неоднозначные
  форматы и серийные числа дат вне ячеек типа date не принимаются.
- Деньги: число, точка/запятая как десятичный разделитель; допустимы пробелы между
  разрядами. Максимум два знака после запятой, модуль до 10¹². Валютные символы,
  бесконечность и текст не принимаются. Все суммы предполагаются в одной валюте.
- `design_approved`, `specification_ready`: да/нет, true/false, yes/no, 1/0.
- `complaint`: необязательный текст описания рекламации или «нет».
- Все остальные ячейки обязательны, кроме фактических дат и `production_start`
  до начала производства. Для начатого/завершённого производства начало обязательно.

Поддерживаемые статусы (неизвестные значения — ошибка, а не молчаливое предположение):

| Источник | Канонические значения | Примеры русских эквивалентов |
| --- | --- | --- |
| CRM | new, measurement, design, production, ready, installation, completed, cancelled | новый, замер, проектирование, производство, готов к монтажу, монтаж, завершён, отменён |
| Замер | planned, in_progress, completed, cancelled | запланирован, в работе, выполнен, отменён |
| Производство | planned, in_progress, completed, cancelled | не начато, в производстве, завершено, отменено |
| Монтаж | planned, in_progress, completed, cancelled | запланирован, в монтаже, выполнен, отменён |

Полный список синонимов — `ALIASES` в `src/validator.py`.

Лимиты: 10 МБ на исходник, 20 МБ на ZIP, 40 МБ распакованных файлов внешнего
архива, 50 МБ распакованного содержимого одного XLSX, 50 000 записей и 100
столбцов на источник, до 100 элементов на архив (включая структуру XLSX).
Относительные пути с `..`, абсолютные пути, обратные слеши, двоеточия,
символические ссылки, шифрование и неоднозначные имена требуемых файлов запрещены.
Ошибки чтения показываются без вывода содержимого файлов.

## Контроль качества и бизнес-правила

Каждая проблема содержит номер заказа, тип, источник, описание, критичность
и, где возможно, номер исходной записи. «Ошибка» означает некорректные или
несогласованные данные; «Предупреждение» — просрочку или отставание CRM от
подтверждённого монтажа. Один заказ может иметь несколько проблем.

Проверяются дубли, отсутствующие источники, записи без CRM, обязательные поля,
даты, суммы, логические флаги и статусы. В том числе:

- завершение без фактической даты и фактическая дата без статуса завершения;
- CRM завершена, но монтаж не подтверждён;
- CRM указывает производство/готовность, но предыдущие этапы не готовы;
- производство без замера, утверждённого проекта или спецификации;
- монтаж без завершённого производства;
- даты этапов раньше заказа, завершение до начала, монтаж до окончания производства;
- плановое окончание производства до начала, готовая спецификация без утверждения;
- будущие даты заказа/фактических событий относительно даты оценки;
- отменённый заказ, который остаётся в работе.

Проверки ячеек и внутристочных противоречий выполняются также для дублей и
записей без CRM. Межисточниковые правила работают по первой записи, как SQL JOIN.
Отсутствие будущего этапа тоже показывается как неполный источник: приложение
не угадывает, что запись ещё не должна существовать.

Текущий этап определяется по подтверждениям источников: выполненный монтаж →
завершён; монтаж в работе или завершённое производство → монтаж; производство
в работе → производство; выполненный замер → проектирование либо производство
при готовых проекте и спецификации. Отмена CRM имеет приоритет.

### Сроки

Для замера, производства и монтажа сравниваются план и факт. Для общего срока
CRM факт монтажа служит приближением выполнения заказа. Завершённый с опозданием
этап остаётся просроченным и после закрытия заказа.

Для незавершённого этапа используется выбранная дата оценки, а не дата из файла:
`max(0, дата оценки − план)`. Будущий план и план на день оценки дают ноль дней.
При отсутствии плана, факте в будущем, отмене или статусе «завершён» без факта
срок невозможно достоверно проверить (NULL); последний случай отдельно является
ошибкой качества. Пустая фактическая дата не означает просрочку сама по себе.
Дни заказа — максимум по этапам, не сумма. График этапов считает один заказ
для каждого нарушенного этапа, включая общий срок; его столбцы нельзя складывать
для получения числа уникальных просроченных заказов.

### Финансы

```text
total_cost = materials_cost + labor_cost + other_cost + installation_cost + delivery_cost
gross_profit = sale_amount − total_cost
margin_percent = gross_profit / sale_amount × 100
```

Нулевая прямая затрата допустима, нулевая выручка не даёт маржинальность.
Отрицательные затраты/выручка, пропуски, непрочитанные суммы и финансовые дубли
блокируют все три расчётных показателя. Потеря отдельных затрат не подменяется
нулём. Статус: «Полные», «Неполные», «Некорректные» или «Неоднозначные (дубли)».
Дубли замеров сами по себе финансовые суммы не изменяют.
Отрицательная прибыль при корректных положительных суммах — допустимый результат.
Арифметика расчёта выполняется через Decimal, SQLite хранит нормализованные суммы
как REAL; интерфейс показывает округлённые значения при необходимости.

Общая маржинальность — `сумма прибыли / сумма выручки × 100` только по финансово
полным заказам; это не среднее процентов. Полные финансы не означают отсутствие
ошибок сроков или статусов. Суммарная стоимость показывает только прочитанные
неотрицательные значения CRM (первая запись дубля); при ошибках она неполная.
Неполные заказы в KPI — заказы с отсутствующим источником, обязательной ячейкой
или финансовым статусом, отличным от «Полные». Записи без CRM не входят в KPI.

Налоги, косвенные расходы, скидки вне `sale_amount`, возвраты и распределение
накладных расходов не учтены. Это **предварительная маржинальность по учтённым
прямым затратам, а не полноценная бухгалтерская прибыль**.

## Экспорт

Раздел «Отчёты» выгружает объединённый реестр и реестр проблем в CSV с русскими
заголовками, UTF-8 с BOM и `;`. Можно скачать весь набор или применить текущие
фильтры соответствующих таблиц. Неизвестные вычисляемые значения остаются пустыми.
Текст, похожий на формулу Excel, экранируется апострофом; числовые отрицательные
результаты остаются числами. Полные оригиналы доступны для просмотра в контроле
качества, но основная выгрузка является реестром с первой записью каждого заказа.

## Демонстрационный сценарий

Предоставленных тестовых файлов в исходном репозитории не было; поэтому создан
синтетический набор, сохранённый в `demo_data`. Это не реальные персональные данные.
Генератор существует для воспроизводимости, но **не нужен при запуске** и
отказывается перезаписывать уже существующие исходники.

Для проверки выберите дату **01.10.2026**:

| Контрольная величина | Ожидаемый результат |
| --- | --- |
| Исходные строки CRM / замер / производство / монтаж | 6 / 7 / 6 / 6 |
| Уникальные заказы CRM | 6 |
| Просроченные заказы | 2 (002 и 004) |
| Заказы с ошибками | 5 |
| Заказы с неполными или ненадёжными данными | 4 |
| Стоимость по учтённым значениям | 650 000 |
| Финансово полные заказы | 2 |
| Взвешенная маржинальность | 44% |
| Заказ 001: затраты / прибыль / маржинальность | 110 000 / 90 000 / 45% |
| Дубли | 003 в производстве |
| Без CRM | 999 в замерах, 888 в монтаже |

002 показывает несогласованное завершение CRM и производство без факта,
004 — отрицательную стоимость материалов, 005 — невозможную дату и отсутствующие
источники, 006 — неуказанные трудозатраты. При другой дате показатели сроков изменятся.

## Тестирование

После установки зависимостей, из корня репозитория:

```bash
python -m pytest -q
python -m pip check
```

Тесты используют фиксированную дату и ожидаемые числа. Проверяются CSV/Excel/ZIP,
отсутствующие файлы и столбцы, лимиты, небезопасные архивы, дубли, LEFT JOIN,
сохранение исходников, независимость SQLite-сессий, статусы, даты, сроки, каждый
компонент затрат, неполные и отрицательные значения, выгрузка с защитой от формул.
Сквозной тест проходит путь ZIP → SQLite → расчёты → CSV. Streamlit AppTest
проверяет демонстрационную загрузку, KPI, графики, фильтры, пересчёт даты и очистку
сессии. Сам факт старта сервера не считается проверкой бизнес-логики.

## Публикация в Streamlit Community Cloud

1. Сохраните файлы проекта в GitHub-репозитории, включая все четыре файла `demo_data`.
   `.venv`, кеши, SQLite-файлы и реальные клиентские данные не публикуйте.
2. В Streamlit Community Cloud выберите **Create app**, репозиторий, нужную ветку
   и основной файл **app.py** в корне.
3. В расширенных настройках выберите **Python 3.12** и запустите публикацию.
   `requirements.txt` установится автоматически; secrets не нужны.
4. После сборки загрузите демонстрационный набор, проверьте контрольные показатели,
   скачайте оба отчёта, затем отдельно проверьте загрузку демонстрационного ZIP.

Установка не зависит от `/workspace`; этот путь используется только вспомогательным
скриптом настройки Codex. Пути demo в приложении определяются относительно `app.py`.
База создаётся в памяти каждой сессии, поэтому не нужна запись в общий файл на Cloud.
Приложение не публикует загруженные файлы в GitHub и не отправляет их во внешние API.
Доступ к опубликованному приложению и данные регулируются настройками платформы.
Развёртывание в Community Cloud описано, но не выполняется автоматически этим проектом.

## Известные ограничения

- Импортирует снимки, не подключается к живой CRM; изменения источников требуют новой загрузки.
- Не исправляет и не записывает ошибки обратно в исходные файлы.
- Дубли выбираются по первой строке, без времени изменения; их нужно разрешать в источнике.
- Отдельный факт доставки отсутствует; для общего срока используется монтаж.
- «Выполненный этап без даты» даёт неизвестный срок, а не автоматически просрочку.
- Все суммы в одной валюте; бухгалтерские правила и косвенные расходы не моделируются.
- Типы статусов, форматы дат, первый лист Excel и UTF-8 ограничены явным контрактом.
- Номер записи включает заголовок; пропущенные пустые строки CSV и многострочные
  поля означают, что он может отличаться от физического номера строки текстового файла.
- Наборы хранятся в памяти, без сохранения между сессиями; лимиты защищают импорт,
  но рекомендуемый демонстрационный объём — сотни/тысячи заказов, не промышленный DWH.
