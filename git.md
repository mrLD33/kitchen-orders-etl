# Порядок работы с Git и GitHub

Эта инструкция применяется ко всем последующим задачам в проекте
`kitchen-orders-etl`. Основная рабочая ветка — **`work`**; целевой репозиторий —
**`https://github.com/mrLD33/kitchen-orders-etl.git`**. Изменения напрямую в `main`
не вносить. Merge в `main` выполнять только с явного разрешения пользователя.

## 1. Проверки перед началом работы

Из корня существующего checkout проверить:

```bash
git branch --show-current
git status --short --branch
git remote -v
git config --get-all remote.origin.fetch
git rev-parse --abbrev-ref --symbolic-full-name '@{upstream}'
git log -5 --oneline
```

Убедиться, что текущая ветка — `work`, адреса fetch и push для `origin`
соответствуют указанному репозиторию, а upstream — `origin/work`.
Не выводить учётные данные из URL или конфигурации авторизации.
Сохранить пользовательские изменения: не перезаписывать и не включать в свои
коммиты посторонние незавершённые правки. Если текущая ветка отличается от `work`,
сначала проверить возможность безопасной работы в `work`; на `main` код не менять.
Использовать существующий изолированный checkout; не создавать Git worktree
без явного запроса пользователя.

## 2. Отслеживание удалённых веток и upstream

Конфигурация `remote.origin.fetch` должна позволять отслеживать удалённые ветки,
включая `origin/work`. Для обычного checkout проекта ожидается:

```text
+refs/heads/*:refs/remotes/origin/*
```

Если единственный refspec ограничен веткой `main`, безопасно расширить его:

```bash
git config --replace-all remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'
git fetch origin
```

Если есть дополнительные нестандартные refspec, сначала изучить их и сохранить
нужные настройки; не заменять неизвестную конфигурацию вслепую.
Знак `+` здесь относится к обновлению локальных remote-tracking ссылок при fetch,
а не к отправке изменений или force push. Fetch не меняет локальные `work` и `main`.

Проверить наличие удалённой ветки чтением:

```bash
git ls-remote --heads origin refs/heads/work
```

Если удалённая `work` существует, после fetch настроить отсутствующий или
неверный upstream локальной `work`:

```bash
git branch --set-upstream-to=origin/work work
```

Если удалённой `work` ещё нет, создать её обычной отправкой существующей локальной
ветки и сразу настроить upstream:

```bash
git push -u origin work
```

Наличие `branch.work.remote=origin` и `branch.work.merge=refs/heads/work` само по
себе недостаточно: локальная ссылка `origin/work` тоже должна существовать.

## 3. Завершение каждого изменения

1. Проверить diff и состояние индекса: `git diff`, `git diff --cached`,
   `git diff --check`, `git status --short --branch`.
2. Запустить соответствующие тесты. Для текущего приложения стандартная команда
   из корня репозитория — `.venv/bin/python -m pytest -q`. Если используется другая
   активированная среда Python 3.12, допустимо `python -m pytest -q`.
   Ошибки исправить и повторно проверить; не заявлять об успешных тестах без запуска.
3. Добавить в индекс только файлы выполненной задачи через
   `git add -- <файлы задачи>`, проверить staged diff и создать коммит с понятным
   сообщением **на английском языке**, например `Fix Plotly chart configuration`.
4. Отправить коммит в `origin/work` обычной командой:

   ```bash
   git push origin work
   ```

5. Проверить успешный код завершения push и фактическое состояние GitHub:

   ```bash
   git rev-parse work
   git ls-remote --heads origin refs/heads/work
   git rev-list --left-right --count origin/work...work
   git status --short --branch
   ```

   В штатном случае полный хеш удалённой `refs/heads/work` совпадает с локальной
   `work`, а счётчики расхождения равны `0 0`. При независимом обновлении GitHub
   обновить ссылки через fetch и проверить наличие отправленного коммита в истории.
   Не считать только локальную ссылку `origin/work` подтверждением состояния сервера.

Если изменения **уже зафиксированы**, повторный коммит не создавать. Проверить
существующий коммит, выполнить тесты и отправить его. Коммитировать только новые
правки; не создавать пустые, повторные или искусственно пересозданные коммиты.

## 4. Диагностика ошибок отправки

При ошибке push самостоятельно прочитать сообщение Git, проверить адреса origin,
текущую ветку, upstream и fetch refspec, состояние рабочего дерева и расхождение
локальной и удалённой истории. Использовать чтение `git ls-remote`, `git fetch
origin`, `git log`, `git rev-list`, `git merge-base --is-ancestor origin/work work`.

Безопасные проблемы конфигурации исправлять самостоятельно и повторять отправку
после проверки исправления. Каждый повтор должен следовать новой диагностике или
изменению состояния, а не повторять ту же ошибку без изменений.

Если удалённая история разошлась с локальной, не перезаписывать её: изучить
расхождения, сохранить пользовательскую работу и согласовать необходимое действие,
если безопасно продолжить невозможно. При подтверждённом отказе в доступе или
недоступной авторизации сообщить конкретный блокирующий фактор. Использовать
имеющуюся платформенную HTTPS-авторизацию; не запрашивать токен только потому,
что `GH_TOKEN` или `GITHUB_TOKEN` не задан.

## 5. Ограничения и итоговый отчёт

- Не применять force push (включая `--force-with-lease`), `git reset --hard`,
  удаление веток, потерю пользовательских файлов и другие потенциально
  разрушительные операции.
- Не выполнять merge в `main` без разрешения пользователя.
- Не создавать повторные коммиты для уже зафиксированных изменений.
- Если пользователь просит только диагностику, не менять конфигурацию, файлы,
  индекс или ссылки; не выполнять commit, fetch или push. Для сравнения с GitHub
  использовать read-only `git ls-remote`.

После завершения задачи сообщить хеш отправленного коммита, название ветки,
результат фактически выполненных тестов и проверку синхронизации с GitHub.
Если отправка не состоялась, явно сообщить об этом и назвать установленную причину.
